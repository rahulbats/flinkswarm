Quick refresher — so the demo lands

What an agent is

  • Unlike an LLM on its own, an agent can take actions — it's a wrapper around an LLM with tools, instructions, and a knowledge base
  • Every call to the LLM carries the tools and instructions; the LLM replies with which tool to run; the agent runs it, feeds the result back, and the loop repeats until the task is done
  • Isolation matters: too many tools in one agent overwhelm the context and cause hallucinations
  • Each agent should run in its own sandbox — a compromised agent must not reach another's data or credentials
03 / 11
The customer

A P&C carrier whose second-largest controllable cost is deciding claims

  • Property & Casualty; millions of dollars in claims a year at very high volume
  • Today a claim sits with an adjuster who reads hundreds of pages, checks the policy language by hand, and researches similar past claims — days per claim, and two adjusters can reach different answers on the same facts
  • The cost of deciding claims — adjuster time, appraisers, reviews — is their largest controllable expense after the claim payouts themselves
  • Board mandate: cut claims cycle time and cost without adding headcount — and every automated decision has to be defensible to a regulator
The ask isn't "add an LLM" — it's coordinating many specialists per claim, at volume, defensibly.
04 / 11
Requirements

What a solution has to do

  • Many specialists per claim, in parallel: claim data, policy coverage, fraud signal, medical review — then one adjudication step
  • Elastic: a catastrophe event can 5–10× daily claim volume for weeks
  • Runs where the data is: some agents on-prem (PII / PHI stays inside the boundary), some in cloud
  • Every input and decision retained and replayable — "why was claim 4471 denied?" answered from a record, not reconstructed
  • Trustworthy decisions: defend against prompt injection and poisoned claim documents; catch model drift as policies and the model change
  • Agents built in-house, each isolated, no runtime lock-in

07 / 11
The proposal

Kafka as the agents' nervous system

  • The customer already runs Kafka for mission-critical event flows — extending it to agent coordination adds no new system of record
  • Tasks are dropped on topics; a distributed swarm of fully isolated agents on containers / VMs picks them up in parallel
  • An agent or service crash simply resumes from the last committed offset — no lost work, no bespoke retry logic
  • Fan-in is a Flink ProcessTableFunction (PTF, Flink 2.1) — keyed state buffers each agent's result and emits one record per claim once all report; the orchestrator runs the final LLM verdict from that
  • No point-to-point calls — agents never talk to each other or the orchestrator; the log is the only thing they share, and every result also feeds fraud analytics, ops, and retraining

Wrap-up

Summary & next steps

the recommendation
  • Coordinate the swarm on the event backbone you already run — not a new engine
  • Agents stay yours: your code, your models, each isolated
  • Flink does the fan-in; the log is the audit trail
  • Distributed, elastic, and explainable at once
next steps
  • A two-week scoping workshop — one experienced adjuster, a non-production claims feed — to put real numbers on cycle time and cost for one claim type
  • Phase 1: shadow mode — the swarm decides alongside your adjusters, nobody acts on it; that comparison is also the first eval baseline
  • Before go-live: a guardrail layer (injection / PII in, decision validation out) and an eval harness that replays claims across model versions to catch drift
  • Adjuster corrections land on their own topic — a labeled dataset that grows itself, feeding periodic fine-tuning
  • Then: an agent-spec.yaml and a K8s operator stand the swarm up; KEDA scales it on lag
