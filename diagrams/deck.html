Background

What are agents

  • Unlike an LLM on its own, an agent can take actions
  • An agent is a wrapper around an LLM with tools, instructions, skills, and a knowledge base
  • Every call to the LLM carries the tools and instructions; the LLM replies with which tool to run. The agent runs it, feeds the result back, and the loop repeats until the task is done
  • Isolation matters. Too many tools overwhelm the LLM context and cause hallucinations
  • Each agent should run in its own sandbox to contain security risk

The customer

A P&C insurer digitizing claims adjudication

  • A Property & Casualty carrier settling millions of dollars in claims at very high annual volume
  • Adjusters read hundreds of pages per claim and research its merits by hand — slow and error-prone
  • Strategic goal: digitize claims review and approval — cut cost and decision time
  • Approach: AI agents that approve / deny / semi-approve a claim
  • Simplified for this talk — three agents:
    • Claims Agent — looks up the claims database for claim details
    • Policy Agent — looks up the object store for the policyholder's policy
    • Coverage Orchestrator — adjudicates from both agents' outputs
  • Each agent runs in its own isolated machine / sandbox — for parallelism and to contain security risk

The proposal

Can Kafka fill this gap?

  • If you already run Kafka for mission-critical event flows, extending it to agent coordination adds no new system of record
  • Tasks that need parallel or sequential execution are dropped on topics; a distributed swarm of fully isolated agents on containers / VMs executes them
  • An agent or service crash simply resumes from the last committed offset
  • Fan-in is a stateful Flink function (PTF) that buffers each agent's result and emits one record per claim once all are in — the orchestrator picks that up and runs the final LLM verdict
  • No point-to-point communication between agents — the log is the only thing they share, and complex workflows compose without much effort

Where this goes

Future considerations

  • The demo is hand-wired — an orchestrator and two workers for one use case
  • Describe the swarm instead in an agent-spec.yaml
  • A Kubernetes operator watches the spec and launches the swarm, using Kafka as the coordination backbone
  • On Kubernetes, KEDA scales each agent on topic lag — swarm capacity follows load, including catastrophe-event spikes
